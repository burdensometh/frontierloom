# V1 persistence format

## Graph manifest

The first two tokens are `FRONTIERLOOM_GRAPH 1`. The remaining records are ordered as follows.

```text
revision REVISION
vertices VERTEX_COUNT
VERTEX_ID  (one token per vertex)
edges EDGE_COUNT
SOURCE_ID DESTINATION_ID  (one pair per edge)
end
```

Revision is a positive unsigned 64-bit integer. External vertex IDs are unsigned 64-bit integers, including zero. All vertices, including isolated vertices, must appear in the vertex list. Edges have a direction. Self-loops are valid. Duplicate vertices, duplicate directed edges and undeclared endpoints are rejected. The loader supports up to 1,000,000 vertices and 4,000,000 edges. The writer emits ascending vertex IDs and lexicographically ordered edges. Dense IDs in snapshots are zero-based indices in ascending external ID order.

The graph identity is 64-bit FNV-1a. Its input starts with the ASCII bytes `FrontierLoom graph v1`, followed by revision, vertex count, ascending vertex IDs, edge count and ordered endpoint IDs as unsigned 64-bit little-endian scalars. A graph revision or changed adjacency produces a distinct input for the identity.

## Superstep checkpoint

The file starts with `FRONTIERLOOM_CHECKPOINT 1` and contains newline-delimited records.

| Record | Fields |
| --- | --- |
| `graph` | Revision and decimal graph identity |
| `program` | Algorithm, BFS source ID or zero for PageRank, damping, tolerance and step limit |
| `cursor` | Next consumable epoch and latest reserved incarnation |
| `placement` | Topology generation, worker count and partition count |
| `owners` | One worker ID per partition in partition order |
| `totals` | Active visits, consumed entries, emitted records, combined entries, recovered failures, resumes, scales and moved partitions |
| `last` | Zero for an initial image, one for a committed superstep |
| `step` | For `last 1`, completed epoch, committing topology, receipt count, active visits, consumed entries, emitted records, dangling mass, L1 residual, total rank mass, combined count, inbox digest and stop reason |
| `mailbox` | Inbox epoch and raw record count |
| `shard` | Partition index, vertex count and combined inbox size, in partition order |
| `vertex` | BFS distance or `inf`, then rank. The records within each shard use increasing dense vertex order. |
| `message` | Dense destination ID and value. Entries follow the state records and use increasing dense destination order. |
| `end` | Terminates the payload |
| `checksum` | Decimal 64-bit FNV-1a over the payload bytes including the newline after `end` |

Program and state floating-point values serialize with 17 significant decimal digits, sufficient to round-trip a binary64. The mailbox digest covers the ASCII domain `FrontierLoom mailbox`, epoch, raw count, and then each shard's entry count and ordered destination and value pairs. Numeric fields other than values use unsigned 64-bit little-endian encoding for the digest. Values use the little-endian binary64 bit pattern. The checksum covers accidental file corruption. Decoding checks version, graph identity, dimensions, partition membership, numerical ranges, mailbox digest and progress consistency.

The first stored epoch has the BFS seed inbox or an empty PageRank inbox. After a barrier commits, the cursor always points to the next inbox epoch, including at a stop marker. The final PageRank scatter can therefore be present even though computation is complete. A placement-generation update keeps the cursor and inbox intact. The last step refers to the topology that committed it, which may precede the current placement.

A writer holds a file lock for the lifetime of the invocation. It creates a temporary file next to the destination, writes and syncs it, renames it over the checkpoint, and syncs the destination directory. Worker incarnations are reserved through the same publication path before opening a new process group. Attempt generation is monotonic within one checkpoint lineage. Recovery starts from the visible committed v1 image.

## Snapshot provenance

`samples/campus.epoch1.v1.flc` is a live snapshot after BFS epoch zero. It contains the settled source and two distance-one messages. It was written by the engine with the following command in a Linux container and is read and resumed by the native snapshot suite.

```sh
build/frontierloom compute --graph samples/campus.v1.graph \
  --checkpoint /tmp/campus.epoch1.v1.flc --algorithm bfs --source 10 --stop-after 1
```

## Sharded V2 snapshot

New snapshots are published as sharded V2 images. `FRONTIERLOOM_CHECKPOINT 1` remains readable, and `convert` rewrites any image, including a stock V1 sample, as V2.

A V2 checkpoint is a small manifest at the checkpoint path plus one shard file per partition under a hidden directory beside it. The manifest carries the same control records as V1 (`graph`, `program`, `cursor`, `placement`, `owners`, `totals`, `last`, optional `step`, `mailbox`), then the sharding records:

| Record | Fields |
| --- | --- |
| `generation` | Digest binding the control image and every shard's size and checksum |
| `previous` | Generation digest the manifest supersedes, or zero |
| `shards` | Number of shard files, equal to the partition count |
| `shard` | Partition index, inbox epoch, byte size and checksum of that shard file |

Records use the same `end` marker and 64-bit FNV-1a checksum trailer as V1. Each shard file is:

```text
FRONTIERLOOM_SHARD 1
graph REVISION GRAPH_IDENTITY
partition INDEX
epoch EPOCH
algorithm bfs|pagerank
vertices COUNT
inbox COUNT
vertex DISTANCE_OR_INF RANK
message DESTINATION VALUE
end
checksum CHECKSUM
```

Shard files live in `<checkpoint>.shards/<generation>/part-NNNN.shard`, where `<generation>` is the 16-digit lowercase hexadecimal form of the manifest's `generation` digest. A shard repeats the graph identity, its partition index, the inbox epoch, the algorithm and the shard-level checksum, so at load time every shard is checked against the graph and against the manifest's advertised size and checksum before any resident state is used.

Publication stages every shard file of the candidate generation, syncs each one and the generation directory, and only then atomically renames the new manifest into place. The manifest rename is the sole commit point:

- If the process dies after saving some but not all shard files, the manifest still names the previous generation. Reading the checkpoint loads the previous complete state, because the half-written shards belong to a generation the manifest does not reference. The bytes of the old shard files are untouched.
- The previous generation directory is retained across one publication so a reader racing the rename, or a manifest rollback, still finds a complete image. Older unreferenced generation directories are pruned after the rename.
- A missing, truncated or corrupt shard file of the *current* generation is rejected as an incomplete generation. Loading never mixes partitions from different generations and never returns a partial frontier.
- Graph identity, the BFS/PageRank superstep cursor, incarnation and the pending inbox are read only from the manifest, which is the single atomic commit point. Resident vertex state comes only from the shard files that generation names.

Repeating `convert` on a V2 image recomputes the same content-addressed generation digest and republishes an identical manifest, so converting the same snapshot twice leaves one visible target. A V1 image converted in place reads back identical before and after, and resumes exactly as the V1 image would.

Control state and resident data are always taken from one complete generation. A reader never observes the new cursor with old vertex state or vice versa.
